<div class="sec-head"><span class="sec-num">1</span><h2 class="sec-title">A matrix is a stack of vectors</h2></div>

You already know a vector like `[3, 4]` is an arrow — magnitude 5, pointing up and to the right. A **matrix** is just several vectors stacked together, row by row or column by column, so you can operate on all of them at once instead of one at a time.

In AI code, that stacking is everywhere: a batch of 32 embeddings is a 32-row matrix; a layer's weights are a matrix that maps an input vector to an output vector; an image is a matrix of pixel intensities. The whole point of learning matrix operations is to stop thinking "loop over vectors" and start thinking "one matrix operation."

Here's the minimal representation we'll build on — no `numpy`, just nested lists, so nothing is hidden:

```python
class Matrix:
    def __init__(self, data: list[list[float]]):
        self.data = data
        self.rows = len(data)
        self.cols = len(data[0]) if data else 0

    def shape(self) -> tuple[int, int]:
        return (self.rows, self.cols)

    def __repr__(self) -> str:
        return "\n".join(str(row) for row in self.data)
```

<Callout label="Where this shows up">
A batch of token embeddings has shape `(batch_size, d_model)`. A weight matrix in a dense layer has shape `(d_in, d_out)`. Every shape mismatch error you'll ever debug in PyTorch is this lesson's rules, enforced by a stricter interpreter.
</Callout>

<div class="sec-head"><span class="sec-num">2</span><h2 class="sec-title">Two kinds of "multiply," and they're not interchangeable</h2></div>

This is the single most common source of shape bugs in ML code, so it's worth being pedantic about it. There are two completely different operations that both get called "multiplying matrices":

- **Element-wise (Hadamard) product:** same-shape matrices, multiply position `(i,j)` by position `(i,j)`. Output is the same shape as the inputs.
- **Matrix multiplication:** row `i` of the left matrix, dot-producted against column `j` of the right matrix, for every `(i,j)`. The inner dimensions have to match, and the output has a *different* shape from either input.

```python
def elementwise_add(A: list[list[float]], B: list[list[float]]) -> list[list[float]]:
    return [[a + b for a, b in zip(row_a, row_b)] for row_a, row_b in zip(A, B)]

def hadamard(A: list[list[float]], B: list[list[float]]) -> list[list[float]]:
    return [[a * b for a, b in zip(row_a, row_b)] for row_a, row_b in zip(A, B)]

def matmul(A: list[list[float]], B: list[list[float]]) -> list[list[float]]:
    rows_A, cols_A = len(A), len(A[0])
    rows_B, cols_B = len(B), len(B[0])
    assert cols_A == rows_B, f"shape mismatch: {cols_A} != {rows_B}"
    return [
        [sum(A[i][k] * B[k][j] for k in range(cols_A)) for j in range(cols_B)]
        for i in range(rows_A)
    ]
```

<Callout label="The bug this prevents" variant="warn">
If you accidentally reach for element-wise multiply where you needed `matmul` (or vice versa), Python/NumPy will often *not* crash — it'll broadcast or silently produce the wrong shape, and you'll debug a "the model won't learn" issue for an hour before noticing. Naming the two operations differently in your head is the fix.
</Callout>

```python
def transpose(A: list[list[float]]) -> list[list[float]]:
    rows, cols = len(A), len(A[0])
    return [[A[i][j] for i in range(rows)] for j in range(cols)]
```

You'll reach for transpose constantly to make shapes line up for matmul — e.g. computing attention scores as `Q @ Kᵀ` so that a `(seq, d)` query matrix can be dot-producted against a `(seq, d)` key matrix to produce a `(seq, seq)` score matrix.

<div class="sec-head"><span class="sec-num">4</span><h2 class="sec-title">The determinant: does this transformation collapse space?</h2></div>

For a square matrix, the **determinant** is a single number that tells you how much the matrix scales area (in 2D) or volume (in 3D) — and whether it flips orientation along the way.

<Formula name="2×2 determinant">
det([[a,b],[c,d]]) = ad − bc
</Formula>

That "singular" case matters directly: a matrix with determinant 0 has no inverse, because it threw away information (multiple inputs now land on the same output point) that no inverse could ever recover.

```python
def det2x2(M: list[list[float]]) -> float:
    (a, b), (c, d) = M
    return a * d - b * c
```

</section>

<section class="lesson">
<div class="sec-head"><span class="sec-num">5</span><h2 class="sec-title">The inverse: undoing a transformation</h2></div>

If matrix `M` transforms space one way, its inverse `M⁻¹` transforms it exactly back: `M⁻¹ M = M I = I`, the identity matrix that leaves everything untouched. It exists **only** when `det(M) ≠ 0` — you can't undo a transformation that already threw information away.

<Formula name="2×2 inverse">
M⁻¹ = (1 / det(M)) · [[d, −b], [−c, a]]  for M = [[a,b],[c,d]]
</Formula>

```python
def inverse2x2(M: list[list[float]]) -> list[list[float]]:
    d = det2x2(M)
    if d == 0:
        raise ValueError("matrix is singular — no inverse exists")
    (a, b), (c, e) = M
    return [[e / d, -b / d], [-c / d, a / d]]
```

Geometrically, the inverse is why solving `Ax = b` for `x` is possible: multiply both sides by `A⁻¹` and you get `x = A⁻¹b`. In practice, deep learning almost never inverts a matrix explicitly — it's expensive and numerically unstable at scale — but the concept underlies why gradient-based optimization exists at all: it's a way of approaching the same answer without ever computing the inverse of a giant matrix.

</section>

<div class="sec-head"><span class="sec-num">6</span><h2 class="sec-title">Broadcasting: how a bias vector adds to a whole batch</h2></div>

```python
def add_bias(X: list[list[float]], b: list[float]) -> list[list[float]]:
    return [[x + bi for x, bi in zip(row, b)] for row in X]
```

<Callout label="The general rule">
Two shapes are broadcast-compatible if, comparing dimensions from the right, each pair is either equal or one of them is 1. `(32, 768)` and `(768,)` broadcast fine — the second is treated as `(1, 768)` and stretched down 32 rows. `(32, 768)` and `(32,)` would not, without reshaping first.
</Callout>

```python
def relu(v: list[float]) -> list[float]:
    return [max(0.0, vi) for vi in v]

def dense_layer(W: list[list[float]], x: list[float], b: list[float]) -> list[float]:
    # W is (d_out, d_in), x is (d_in,) treated as a column
    z = [sum(W[i][k] * x[k] for k in range(len(x))) for i in range(len(W))]
    z = [zi + bi for zi, bi in zip(z, b)]
    return relu(z)
```

Stack a few of these, each with its own `W` and `b`, and you have a multi-layer perceptron. Everything past this point — CNNs, transformers, diffusion models — is this same pattern with more structure imposed on `W`.
